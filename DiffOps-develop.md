## 3. DECISÕES DE ARQUITETURA (rationale para a banca)

| # | Decisão | Rationale |
|---|---|---|
| D1 | **Auth JWT stateless** (Supabase Auth + VerifySupabaseJwt) em web e mobile | Mesma identidade nos dois clientes; sem sincronização frágil de sessão Laravel↔Supabase; Laravel stateless |
| D2 | **Supabase Cloud free como fonte única** (DB+Auth+Realtime) em todos os ambientes | Evita divergência de Realtime/RLS entre local e produção |
| D3 | **Laravel é o único escritor**; service role exclusiva no servidor; clientes só leem (API/Realtime) | Evita corridas de escrita, inconsistência e vazamento de chave |
| D4 | **Heurística local como ancora + fallback da IA** | Determinística e barata; sustenta análise quando a IA falha/limita |
| D5 | **Arquitetura 100% padrão Laravel 12** (diretórios do scaffold; Api/ e Web/ só dentro de Controllers; Services/ por convenção) | Facilita manutenção e defesa do TCC; nada de estrutura customizada |
| D6 | **Pipeline 4 agentes + skills** (planner/builder/tester/orchestrator) | Qualidade por etapas; testes sempre antes do código |
| D7 | **Git**: branches `@user/num/tipo/desc`; commits atômicos convencionais; push só com aprovação do usuário | Rastreabilidade da evolução; atomicidade = 1 unidade lógica por commit |
| D8 | **Design System TACTICAL OPS** com tokens compartilhados (Tailwind/NativeWind) | Paridade visual web/mobile com identidade militar-tática |
| D9 | **RLS/triggers/Realtime via migrations Laravel** (guardadas por driver; SQL versionado; `supabase/migrations/` reservado com README) | Fonte única versionada e reproduzível; SQL solto no editor do Supabase gera drift |
| D10 | **Stack 100% conteinerizada** (app/nginx/node/redis/horizon) + horizon/predis no composer | Testes e migrate rodam no container com pdo_sqlite/pdo_pgsql/pcntl (PHP local não tem as extensões) |
| D11 | **Merge em `main` exclusivamente via Pull Request** (ORCHESTRATOR abre a PR; usuário revisa e mergeia; agente nunca mergeia) | Rastreabilidade e controle total das integrações; CI valida toda PR |
| D12 | **CI no GitHub Actions** (backend: pint + pest em SQLite offline; frontend: build assets) — sem credenciais no CI | Qualidade automatizada nas PRs com custo zero |
| D13 | **`firebase/php-jwt ^7.0` como biblioteca JWT** — `^6.0` (previsto no plano) é bloqueado pelo Composer por advisory de segurança (PKSA-y2cr-5h3j-g3ys / CVE-2025-45769, chaves HMAC fracas, afetadas < 7.0.0); o v7 exige `Key` com algoritmo explícito (allow-list por objeto, sem o terceiro parâmetro `$algorithms` do v6) e valida tamanho mínimo de chave HMAC (≥ 256 bits p/ HS256, ≥ 512 p/ HS512) | Dependência corrigida e sem vulnerabilidade conhecida; `Key` elimina a classe de bug de algorithm confusion |
| D9 | **Stack 100% conteinerizada para dev/testes** (php-fpm + nginx + node + redis + horizon via docker-compose; vendor na imagem com bind `.:/var/www`; entrypoint ajusta permissões do storage em runtime) | Contorna a falta de pdo_pgsql/pdo_sqlite no PHP local; `migrate` e testes rodam no container com os drivers reais; bind mount mantém o ciclo de edição rápido |
| D10 | **Horizon + Predis como dependências do composer** (`laravel/horizon ^5.48`, `predis/predis ^3.6`) | O serviço horizon do compose executa `php artisan horizon` (precisa do pacote) e o `.env` usa `REDIS_CLIENT=predis` (precisa do client predis — ausentes no scaffold da U1) |
| D14 | **JWKS/RS256 com HS256 como caminho principal + fail-closed** — o `SupabaseJwtService` roteia por `alg` do header: HS256 segue o secret compartilhado (Supabase Cloud emite HS256); RS256 resolve a chave via `SupabaseJwksService` (cache Redis + refetch único por `kid` desconhecido) e rejeita qualquer outro `alg`; se o JWKS falhar (HTTP/parse), o RS256 falha fechado (exceção, nunca degrada para aceitar token inválido) | Cobre a rotação de chaves do blueprint (§11.3) SEM quebrar o emissor HS256 do Supabase Cloud; allow-list rígida por `Key` + fail-closed mantém a segurança |
| D15 | **Lazy profile sync no login (ProfileSyncService)** — o guard cria o perfil local no 1º login (`firstOrCreate` por `supabase_uid`) e sincroniza claims apenas quando mudam; `last_login_at` com debounce (`Cache::add` + `last_login_debounce`); falha de sync em user existente é reportada mas NUNCA derruba a autenticação; falha na criação propaga (fail-closed) | DifOps não depende de seed manual de usuários; hot login loop não martela o banco; autenticação nunca depende do estado do perfil |
| D16 | **Revogação ativa de tokens FORA DE ESCOPO DEFINITIVO** — o GoTrue/Supabase Auth não expõe revogação programática de access token (o client pode revogar refresh tokens via `logout`, mas não há API de servidor para invalidar um access JWT emitido); qualquer tentativa de denylist/blacklist no Laravel seria uma cópia local da chave com risco de drift e falso sentimento de segurança. **A alavanca real de acesso é `users.is_active`** (U9): o guard rejeita `is_active === false` a cada request, o que torna a revogação efetiva em segundos (próxima request falha) SEM depender de estado do token. RBAC/gates finos (commander por recurso) ficam para a Fase D junto com as rotas de ingestão; `last_login_at` segue com debounce (U10) e o profile sync HTTP (U11) NUNCA altera flags operacionais | Alinhado ao contrato de segurança da banca (revogação deve ser imediata e auditável); `is_active` já é a única fonte de verdade de acesso; evita engenharia frágil sobre um recurso inexistente no provedor |
| D17 | **Profile sync HTTP opt-in (U11): claims do JWT são a fonte primária; o fetch preenche APENAS lacunas** — o `SupabaseProfileFetcher` busca o perfil GoTrue (`/auth/v1/user`) com o Bearer token do request quando `profile_sync_http=true`; valor presente na claim (não-null, não-string-vazia p/ strings) VENCE; campos ausentes/vazios são preenchidos pelo fetch; flags operacionais (`is_active`, `is_commander`, `preferences`) NUNCA vêm do fetch; falha do fetch é reportada e NUNCA derruba auth (create e refresh) — falha de escrita no DB continua fail-closed; resposta cacheada por `sha256(token)` com TTL próprio; **flag off (default) ou token null → comportamento idêntico ao U10 (zero rede)** | Enriquecimento de perfil sem duplicar fonte de verdade (GoTrue é o dono do perfil); contrato de merge determinístico; degradação graciosa mantém auth estável; opt-in preserva a suíte 100% offline e o custo zero de rede por default |

## 5. DESVIOS DO BLUEPRINT

> Registrar aqui TODA divergência entre o código real e o `DiffOps.md`, com motivo.

- **D-U8-1: `RepoWatchlist` SEM `$primaryKey` custom (array) — PK composta documentada no docblock** — a tabela `repo_watchlist` não tem coluna `id` e a PK é composta (`repo_watchlist_pk` user_id+repository_id); um `protected $primaryKey = ['user_id', 'repository_id']` (array) quebraria o Eloquent com TypeError em `find()`/`update()`/`delete()`. O model declara `public $incrementing = false` (sem autoincremento) e documenta no docblock que o acesso é por query composta `where('user_id', ...)->where('repository_id', ...)`; `find()`/`update()`/`delete()` de instância NÃO são suportados. Motivo: a chave natural é a garantia de unicidade do banco (U7); o Eloquent não lida com PKs compostas de forma segura neste cenário.
- **D-U8-2: `Repository` SEM relation `pullRequests`** — a tabela `pull_requests` é denormalizada (sem FK para `repositories`, decisão U7): um `hasMany(PullRequest::class)` não tem coluna de FK para se basear. O model documenta no docblock que PRs de um repositório são buscadas por `where('organization_id', ...)->where('github_repo_id', ...)`. Motivo: coerência com o schema real; evitar uma relation quebrada que daria `null`/erro em runtime.
- **D-U8-3: `Repository::watchlistUsers()` BelongsToMany SEM `withPivot`** — o pivot `repo_watchlist` só tem `created_at` (append-only, sem timestamps completos); `withPivot('created_at')` não é necessário para o uso atual e exporia a data na serialização sem necessidade. Motivo: contrato mínimo; o accessor `watchlistEntries()` (HasMany) existe para consultas diretas ao pivot.
- **D-U8-4: `User` NÃO alterado na U8** — o plano de models previa (em rascunho) uma relation `watchlistRepositories()` no `User`, mas a U8 entrega apenas os 5 models de FEATURES; `User` fica intacto (o plano aprovado não pede alteração em User). Motivo: escopo da unidade; a relation no User (se necessária) entra em uma unidade futura que mexa em User.

Motivo: D14 — compatibilidade com o emissor real + cobertura da rotação de chaves sem abrir classe de algoritmo.

Motivo: o plano dizia "8 testes U9 permanecem verdes SEM alteração", mas isso é mutuamente exclusivo com o próprio comportamento novo de criar perfil no 1º login — o plano priorizou a criação (ProfileSyncTest + guard cria perfil), então os 2 testes de cenário obsoleto acompanharam a realidade. Os outros 9 testes do guard e 10 do middleware permaneceram intactos.
- **D-U11-1: nenhum teste existente foi editado (diferente da U10) e o helper do feature test foi renomeado para `profileHttpSyncUrl`** — o plano pedia helpers `profileHttp*`; o `profileHttpUrl()` global declarado em `SupabaseProfileFetcherTest` (unit) colidiria com o mesmo nome em `ProfileSyncHttpTest` (feature) → "Cannot redeclare" quando os dois arquivos rodam no mesmo processo Pest. Motivo: armadilha recorrente de funções globais Pest (U5–U10); zero edição em testes U9/U10.

## 6. ARMADILHAS & APRENDIZADOS

- **U8: PK composta sem `$primaryKey` — `getKey()` retorna `null` e `find()`/`update()`/`delete()` de instância NÃO funcionam** — `RepoWatchlist` não tem coluna `id`; sem `$primaryKey` custom (um array quebraria o Eloquent com TypeError), o `create()` funciona (insert sem retornar id, `getKey()` → null), mas `find($id)`/`$entry->update()`/`$entry->delete()` não são suportados.
